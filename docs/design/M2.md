# Design M2: tags, full-text search and Postgres-backed rate limits

Builds on `docs/design/M1.md` and decisions `0001`–`0005`. Everything M1 defines stays; this doc lists what M2 adds or changes. Choices that differ from the spec's Data sketch are in `docs/decisions/0005-m2-design.md`.

## Features
Every protected route built in M2 (F101–F104) documents `rateLimitedResponse` (429) from the scaffold's `src/lib/rate-limit.ts`. Files a feature changes beyond its backlog `touches` are named below; the scheduler does not know about them, so the owner should align `touches` with `/replan`.
- F101 tag: `bookmark_tags` table, `TagName` schema, `lib/tags.addTag`, `PUT /bookmarks/{id}/tags/{tag}`; `lib/bookmarks` fills `Bookmark.tags` (sorted by name) on every route.
- F102 untag: `lib/tags.removeTag`, `DELETE /bookmarks/{id}/tags/{tag}`.
- F103 tag list: `lib/tags.listTags`, `GET /tags`.
- F104 rename/merge: `lib/tags.renameTag`, `PATCH /tags/{name}`.
- F105 tag filter: `tag` query param on `GET /bookmarks`.
- F106 search: `bookmarks.search` generated column + GIN index, `q` query param on `GET /bookmarks`.
- F107 write limit: `rate_limits` table, `lib/rate-limit.hit`, the check inside `requireAuth` with both branches (writes with `RATE_LIMIT_WRITE_PER_MIN`, GETs with `RATE_LIMIT_READ_PER_MIN`), so only F107 and F109 edit `src/lib/auth.ts`. Also adds `rateLimitedResponse` to every M1 protected route (`src/routes/auth.ts` sign-out, `src/routes/me.ts`, `src/routes/bookmarks.ts`) and regenerates `openapi.json`.
- F108 read limit: its own test and verification of the GET branch F107 built; no change to `src/lib/auth.ts`; if its test finds a bug there, the feature is `needs_human` rather than editing an undeclared file.
- F109 sign-in limit: `lib/rate-limit.hit` called by sign-in, keyed by email; adds `rateLimitedResponse` to `POST /auth/sign-in`.
- F110 latency budget: new `perf.config.json` entries, tagged seed data (see NFR).
- F111 contract coverage: the statuses listed under Contract.

## Data model
Schema in `src/db/schema.ts`. M1 tables unchanged except `bookmarks` gains one column, one unique and one index.

- **bookmarks** (additions):
  - `search tsvector generated always as (to_tsvector('simple', title || ' ' || coalesce(note, '') || ' ' || url)) stored`. Postgres keeps it current on insert and update; the app never writes or returns it (mapping to `Bookmark` picks fields explicitly).
  - `bookmarks_search_idx` GIN on `search`.
  - `bookmarks_id_user_uq` unique on `(id, user_id)`: the target of `bookmark_tags`' composite FK.
- **bookmark_tags**: `bookmark_id uuid not null`, `user_id uuid not null`, `name text not null` (lowercase, `^[a-z0-9-]{1,32}$`, checked by zod at the boundary).
  - PK `(bookmark_id, name)`: a bookmark carries a tag at most once; `PUT` is `insert … on conflict do nothing`. Also serves the tag filter's per-bookmark probe (0006).
  - FK `(bookmark_id, user_id) → bookmarks(id, user_id) on delete cascade`: a tag row can only carry its bookmark's owner, and deleting a bookmark (or its user, via the bookmarks cascade) removes its tags.
  - `bookmark_tags_user_name_idx` on `(user_id, name)`: serves `GET /tags` and rename.
  - There is no separate `tags` table: a tag is a name that some bookmark of the user carries, so "a tag on no bookmark is not listed" holds without cleanup (0005).
- **rate_limits**: `key text not null`, `window_start timestamptz not null`, `count integer not null`; PK `(key, window_start)`. Keys: `write:<token_id>`, `read:<token_id>`, `sign-in:<lowercased email>`. Rows of older windows for a key are deleted by the same statement that counts that key's next hit, so the table holds at most one row per key ever used (including revoked tokens and every email tried at sign-in). That growth is unbounded but a few dozen bytes per key; accepted for a local, single-owner API with no cleanup job.
- Access rules (unchanged from M1, no RLS): every query on `bookmark_tags` lives in `src/lib` and is scoped to the caller: it filters `user_id = $u`, except the `GET /bookmarks` tag filter, which is correlated to `b.id` under `b.user_id = $u` and relies on the composite FK (0006); `rate_limits` is touched only by `lib/rate-limit`.

### Migrations
1. `drizzle/0001_m2_tags_search_rate_limits.sql` (built in this branch, Shared scaffold): create `bookmark_tags` and `rate_limits`; add the generated `bookmarks.search` column (backfilled by Postgres from existing rows); add `bookmarks_id_user_uq` before the FK that references it; add the two indexes. Additive only; the rollback comment drops what it adds. M2 features add no further migrations.

## Contract
Generated `openapi.json`. Error body, validation hook, auth-before-validation order and `{id}` handling as in M1. `Bookmark.tags` is now the bookmark's tag names sorted by name. `TagName` (in `lib/tags`): `z.string().transform(s => s.toLowerCase()).pipe(z.string().regex(/^[a-z0-9-]{1,32}$/))`, so a failure names the field (`tag`, `name`).

| Route | Auth | Params / body / query | Success | Errors |
|---|---|---|---|---|
| `PUT /bookmarks/{id}/tags/{tag}` | bearer | `tag`: `TagName` | 200 `Bookmark` | 400 validation_error / too_many_tags, 401, 404, 429 |
| `DELETE /bookmarks/{id}/tags/{tag}` | bearer | `tag`: `TagName` | 200 `Bookmark` | 400, 401, 404, 429 |
| `GET /tags` | bearer | – | 200 `{ items: [{ name, count }] }` by name | 401, 429 |
| `PATCH /tags/{name}` | bearer | path `name`: `z.string()`; body `{ name: TagName }` | 200 `{ name, count }` | 400 (body `name`), 401, 404, 429 |
| `GET /bookmarks` (changed) | bearer | M1 params + `tag?: TagName`, `q?: string` (≤ 500 chars) | 200 `Page<Bookmark>` | 400 validation_error / invalid_cursor, 401, 429 |
| `POST /auth/sign-in` (changed) | public | – | – | adds 429 |
| every other M1 bearer route | bearer | – | – | adds 429 |

Every 429 is `rate_limited` with header `Retry-After` (integer seconds, ≥ 1), documented in `responses` with `headers`. `lib/rate-limit` exports `rateLimitedResponse` (the 429 `responses` entry) so every route documents it the same way. Sign-up, `/health` and `/openapi.json` have no 429.

Rules:
- **Tag order of checks.** auth (401) → rate limit (429) → validation (400) → owner lookup (404) → limit (`too_many_tags`). `PATCH /tags/{name}`: the path name is lowercased and looked up; a name no bookmark of the caller carries (including one that could never be valid) is 404 `not_found`.
- **Add** (one transaction): `select id from bookmarks where id = $id and user_id = $u for update` (none → 404); if the tag is already on it → return the bookmark; if it already has 10 tags → 400 `too_many_tags`; else insert. The row lock makes two concurrent adds unable to reach 11. Tag changes do not touch `updated_at`.
- **Remove**: owner lookup (404), `delete … where bookmark_id = $id and user_id = $u and name = $tag`, return the bookmark.
- **List**: `select name, count(*) from bookmark_tags where user_id = $u group by name order by name`.
- **Rename** `old → new` (one transaction): `old = new` → return its count; else `insert into bookmark_tags (bookmark_id, user_id, name) select bookmark_id, user_id, $new from bookmark_tags where user_id = $u and name = $old on conflict do nothing`, then `delete … where user_id = $u and name = $old` (0 rows deleted → 404 and roll back), then return `{ name: new, count }`. A bookmark that had both keeps one `new`, so its count only falls.
- **Filters on `GET /bookmarks`** add to M1's page query with `and`: `tag` → `exists (select 1 from bookmark_tags t where t.bookmark_id = b.id and t.name = $tag)` (no `t.user_id`: `b.user_id = $u` scopes it and the composite FK gives the tag row its bookmark's owner; with it, stale stats let the planner nested-loop over the user's whole tag set, 0006); `q` → trimmed, empty means absent, else `b.search @@ plainto_tsquery('simple', $q)`. Order and cursor are M1's (`created_at desc, id desc`), never rank. A `q` with no searchable word matches nothing. Cursors carry no filters; the client repeats them.
- **Rate limit** (`lib/rate-limit.hit(key, limit, windowSeconds)`), one statement, Postgres clock:
  ```sql
  with old as (delete from rate_limits where key = $k and window_start < date_bin($w, now(), 'epoch')),
  hit as (insert into rate_limits (key, window_start, count) values ($k, date_bin($w, now(), 'epoch'), 1)
          on conflict (key, window_start) do update set count = rate_limits.count + 1
          returning count, window_start)
  select count, greatest(1, ceil(extract(epoch from window_start + $w - now())))::int as retry_after from hit
  ```
  `$w` is an interval (`make_interval(secs => windowSeconds)`). `count > limit` → 429 with `Retry-After: retry_after`. Rejected hits count too.
  - `requireAuth` (lib/auth), after the token is valid: `GET` → `hit("read:"+tokenId, RATE_LIMIT_READ_PER_MIN, 60)`, any other method → `hit("write:"+tokenId, RATE_LIMIT_WRITE_PER_MIN, 60)`. Sign-out counts as a write (0003). No route file changes for the check itself.
  - Sign-in: after body validation, before the user lookup and password check: `hit("sign-in:"+email, 10, 900)`. A malformed body is 400 and not counted.
  - `lib/env` has `RATE_LIMIT_WRITE_PER_MIN` (default 60) and `RATE_LIMIT_READ_PER_MIN` (default 300), positive integers (scaffold). The sign-in limit is fixed.
  - **Window boundaries in tests.** A test that bursts to a limit (F107's 61 writes, F108's 301 reads, F109's 11 sign-ins) first reads the Postgres clock (`select now()` through `src/db`) and waits until at least 20 s remain in the current window (60 s, or 900 s for sign-in, aligned to the epoch), so the whole burst lands in one window. The verifier does the same, or retries once when its burst crosses a boundary. Such tests set an explicit per-test timeout (Vitest's default is 5 s; the wait can reach 20 s, and F107's "wait Retry-After" case up to 60 s more).

## Modules
Unchanged from M1, plus:
- `src/routes/tags.ts`: the four tag routes (both `/bookmarks/{id}/tags/{tag}` routes and both `/tags` routes), mounted in `src/app.ts`.
- `src/lib/tags.ts`: `TagName`, every `bookmark_tags` query (add, remove, list, rename), each scoped by `userId`. Imports `lib/bookmarks` to return the bookmark after a change.
- `src/lib/bookmarks.ts`: also reads tags for each returned bookmark (one aggregated subquery or one `where bookmark_id = any(...)` query per page, never one query per row) and applies the `tag` / `q` filters. Never imports `lib/tags` (the import goes one way); takes the already-validated tag name.
- `src/lib/rate-limit.ts`: `rateLimitedResponse` (scaffold: the 429 `responses` entry with its `Retry-After` header and `rate_limited` body), and `hit` plus setting the 429 and `Retry-After` (F107). Imports `db`, `lib/env`, `lib/errors`; imported by `lib/auth` and by routes (for the 429 schema).

Import rules (`.dependency-cruiser.cjs`), in addition to M1's: `lib/bookmarks` does not import `lib/tags` (`bookmarks-not-tags`); `lib/rate-limit` does not import `lib/auth` (`rate-limit-not-auth`), so `lib/auth → lib/rate-limit` cannot form a cycle. Routes still reach data only through lib.

## Shared scaffold
Built in this branch: the M2 tables, column, constraint and indexes in `src/db/schema.ts` and migration `drizzle/0001_m2_tags_search_rate_limits.sql` (F101–F106 and F107–F109 all need them; one migration avoids parallel lanes each generating a `0001_*`). Also the two dependency-cruiser rules above, and, because F101–F104 and F107–F109 all need them: `src/lib/rate-limit.ts` with only `rateLimitedResponse` (and a schema test), the two `RATE_LIMIT_*` variables in `src/lib/env.ts`, and the `perf` npm script running with both set to 1000000. Nothing else: no routes, no counting and no tag logic; features build those. Features whose `touches` list `src/db/schema.ts` or `drizzle/**` should not need to change them.

## NFR
- Load: as M1: one owner, a few requests per second, ~1,000 bookmarks per user, up to 10 tags each. Rate-limit counting adds one indexed upsert per authenticated request (~1 ms). p99 < 150 ms locally with 1,000 bookmarks for `GET /bookmarks?tag=<tag>`, `GET /bookmarks?q=<word>`, `GET /bookmarks?q=<word>&tag=<tag>&status=unread` and `GET /tags` (F110 adds these to `perf.config.json`, `auth: true`, `p99: 150`; its seed tags every bookmark with one of a few tags and puts a known word in some notes).
- Rate limits vs load tools: `npm run perf` seeds 1,000 bookmarks and sends thousands of reads with one token, which the real limits would reject. The scaffold makes the `perf` script run with `RATE_LIMIT_WRITE_PER_MIN=1000000 RATE_LIMIT_READ_PER_MIN=1000000`. Vitest and `./init.sh` use the spec defaults, so a test needing more than 60 writes or 300 reads per minute gets more tokens through sign-in (or seeds through `src/lib` directly); F107 and F108 run the whole suite and fix their own breakage, not by raising limits in tests.
- Security: attacker as M1 (no token, or another account holder), plus anyone guessing passwords. Stops: tag routes run `requireAuth` per route (0002) and every `bookmark_tags` query filters by `user_id` or is correlated to a bookmark already scoped by `b.user_id` (the tag filter, 0006); the composite FK makes a tag row on another user's bookmark impossible even after a lib bug; tag names, `q` and the rename target go only through bound parameters (`plainto_tsquery`, never `to_tsquery` on raw input, so no tsquery syntax errors as 500s); `q` capped at 500 chars. Rate limits bound write and read volume per token (and `rate_limits` grows by one small row per new key, see Data model) and password guessing to 10 per 15 minutes per email; counting happens before the password check and whether or not the email exists, so 429s reveal nothing about accounts. Keys hold token ids, never tokens. The sign-in limit lets anyone lock an email out of sign-in for up to 15 minutes; existing tokens keep working, which is acceptable for one owner.
- Cost: local only; no new infrastructure (no Redis). $0.

## Decisions
- One `bookmark_tags` table instead of `tags` + `bookmark_tags`: no orphan tags to clean up, rename is two statements, and counts are a `group by` on an index. Rejected: a `tags` table with ids (needs cleanup on remove and a merge across two tables). 0005.
- Search as a stored generated `tsvector` with a GIN index, matched by `plainto_tsquery('simple', q)`. Rejected: computing `to_tsvector` per query (no index) and `websearch_to_tsquery` (operators the spec does not ask for).
- Rate-limit check inside `requireAuth`, not a separate per-route middleware: every protected route already runs it, so no route can forget the limit, and 0002's per-route rule still holds. 0005.
- Fixed windows with `date_bin` on the Postgres clock and one upsert statement: atomic across concurrent requests and app processes. Rejected: in-memory counters (spec says Postgres) and a periodic cleanup job (the per-key delete keeps the table small).
- Env overrides for the per-token limits, used only by `npm run perf`. Rejected: disabling limits in perf (would hide the counting cost from the latency budget). 0005.
- `q` longer than 500 chars is 400 naming `q`: bounds parse and match cost; the spec gives no limit. 0005.
